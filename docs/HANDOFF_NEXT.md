## 1. 项目是什么 + 当前基线数字

**一句话**：rfauto 是射频/微波设计与仿真的自动化框架——描述器件，闭式
物理公式给出第一版尺寸，接 16 个电磁/EDA 引擎求解，质检门判断结果可不可信，
优化器闭环；AI 助手可以经 MCP 指挥全流程，但只有一条铁律：**所有物理数字
只由确定性内核或求解器产生**。对外发布面（双语 README、CHANGELOG、发布
流程）在 `release/rfauto_public/`。

## 2. 已定决策十条（不要推翻，除非用户主动提出）

- **D1 分层不可破**：cli/mcp_server → service → linkage/optimization/models
  → adapters → pipeline → infra → core，import-linter 强制；新增"可替换
  组件"一律用 基类+注册表 模式。
- **D2 服务层 JSON 进出**：新功能先写 service 函数，CLI/MCP 只做薄壳；
  MCP 入口必须零 stdout 打印（stdio 传输把 stdout 当 JSON-RPC 信道）。
- **D3 数值只在确定性内核**：LLM/agent 永不产生物理数字，只产出 typed
  tool call；评审与纠偏必须是 service 层确定性函数，LLM 只编排与解释。
- **D4 Agent 写面隔离**：agent 对工作区的一切自主修改走沙箱草稿 → 既有
  三层 Gate promote；不给 agent 配直接写工作区的工具。
- **D5 真机对齐基准=HFSS**：其他引擎/设计值向 HFSS 仲裁对齐；远程求解机
  的商用工具版本必须与本机完全一致（数值可比性硬约束）。
- **D6 测试红线**：改码前先跑基线、改完必须全绿；终门=分段独立进程串行
  （内建尾段自动重试只用于环境类定性）；**真红永不隔离、不凑绿**——
  判 FAIL 是有效产出，事后改判据才是事故。
- **D7 上传零敏感**：一切对外上传去除全部敏感信息（绝对路径、主机名、
  凭据、内部账本语义）并实测干净环境可用；GitHub 的 issue/PR/评论**永远
  人工执行**，AI 只负责公开仓 push 与 CI 状态检查。
- **D8 观测性 best-effort**：provenance/日志/审计不得成为业务主路径的
  故障点，宁可记 unknown 也不阻塞真机求解。
- **D9 远程执行纪律**：可上远程服务器的计算环节一律优先上服务器，本机只
  留编排与轻计算；服务器侧临时文件放指定数据盘专用根、禁写生产同步盘；
  每机互斥；任务毕必须清理（杀残留进程、删计划任务）。
- **D10 文档账本同步**：每次实质性改动同笔更新开发日志与待办清单并
  commit；文档数字与代码冲突时以实测为准并当场修正。

## 3. 风格守则十条（用户可见文案动笔前读）

1. **一句一个括号**：一句话里出现第二个括号补注，就把其中一个化进正文
   或拆句。
2. **诚实靠展示，不靠反复声明**："如实/不猜/不编/不凑绿"全仓用户可见面
   限用一次——诚实是显示 UNKNOWN、显示"0 条"，不是反复说自己诚实。
   写完 grep 一遍"如实"，超过 1 处就重写。
3. **名词不超过三连**："跨保真门历史"这类压缩句拆成"X 的历史"，让句子
   里有动词。
4. **代号三审**：席号/批次号/战役代号一律删；项目代号首现给全称、正文
   少用；`#NNN` 坑号保留（数字出处标记）但少当论据。
5. **用户界面不出现内部账本词**：口径、门号、实装实测、发射、下发、
   座位、立战役、放行——换成 约定、检查、已安装的版本、发送、阶段任务、
   创建、禁用。
6. **中文文案里的英文词只留协议名**（run/adapter/trial/cost 这类有键名
   的），其余给中文并括号注一次（"仿真通道（adapter）"），全站用词同一。
7. **数字单一出处**：同一文档同一事实只用一个数；写完对一遍
   check_numbers 锚值——历史上 77/71/72、+9/+7 一类漂移全是手写数字惹的。
8. **"不是A而是B"每篇最多 1 处**；排比三连出现时先问"这句真的需要气势吗"。
9. **技术表述与叙事分开**：表格/参数表/JSON 示例里术语照旧；叙事段
   （场景、为什么、怎么办）说人话。
10. **改完朗读一遍**：读起来像同事在旁边讲解的就过关；像宣读决议的
    （"如实声明""显式警示""先行核验再生效"）回炉。

## 6. 新席开工指引

**开工顺序**（每次会话开始按序读）：

1. `AGENTS.md` 全文（行为约束与踩坑速查——坑号条目按主题检索，勿通读硬背）；
2. 本文件（§1 数字 → §2 决策 → §3 守则 → §4 你要做的条目）；
3. `TODO.md` 现行版（§〇 欠账 / §二 裁决点 / §三 用户侧阻塞勿碰清单）；
4. 最近一次战役的 `runs/<战役>/SUMMARY.md`（当前状态全景）；
5. `scripts/check_numbers.py` 实测一遍，对上 §1 表格再动手。

**基线与门**：

- 改任何代码前跑 `.venv/Scripts/python.exe -m pytest tests/unit -q` 记基线，
  改完全绿才算完；
- 合流预检跑 `scripts/merge_preflight.py`（约 2 分钟），把漂移类失败消化
  在席位内；
- 日常门可并行，**终门必须串行分段**（`wf_gate_full` 命名口径）；门失败
  先定性（环境类/基础设施类/真红三分法）再动手，勿反复重跑烧时间；
- 凡"存在配置就走外部服务"的分支，相关单测必须钉住通道，禁止网络依赖。

**子代理三禁**：不 commit、不写账本文档（开发日志/待办/正式 docs）、
不跑全量门；报告"全绿"后主代理必须独立复跑再验收。实现类长任务并发
≤3-4；共享文件先完成先合流，避免整文件暂存捎带他轨改动。

**文件面纪律**：任务书必须显式写"文件面 + 禁改清单"；会话一次性产物
（探针脚本、扫描报告、散装日志）一律落 `runs/`（证据区）或用毕即删；
收尾清点必含 `git status` 加根目录与发布根的 `ls` 抽查。

**提交纪律**：代码 commit 同笔带开发日志条目；提交信息含代码或产物改动
一律带 `wf:<id>` 标记；提交前对新增中文文件抽查是否有乱码替换字符。
