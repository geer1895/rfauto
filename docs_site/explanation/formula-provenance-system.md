# 解释：公式出处注册表与精度档案体系

> 这是一篇 explanation（解释文）：回答"为什么 rfauto 要给每条公式
> 建一套出处登记制度、它为什么长成三载体+幂等再生的样子"，不教操作。
> 操作面：docs/how-to/formula-provenance.md（声明写法与再生步骤）；
> 上位原理：docs/explanation/deterministic-kernel.md（数值只在确定性
> 内核）、docs/explanation/anchor-and-verdict.md（锚与判据）。

## 问题的三层：这个数字从哪来

拿到任何一个物理数字（"这条 50Ω 线衰减 0.21 dB/cm"），可信度取决于
能否回答三层问题：

1. **谁算的**——哪段代码、哪个 commit、什么输入（可重放性）；
2. **哪条公式**——函数体里的闭式是谁的（Hammerstad-Jensen？Cohn？
   还是实现者"调出来的"）；
3. **哪个来源**——那条公式核对过原文吗，偏差分档与有效域是什么。

docs/explanation/deterministic-kernel.md 回答第 1 层（确定性产地+
注册表+锚）。本文讲第 2、3 层的制度化：**公式出处注册表（KD-1，
knowledge/formula_provenance.yaml）与精度档案（XC-P，
knowledge/precision_profiles.yaml）**。没有它们，"确定性内核"只是
跑得快的黑箱——公式对不对、能用到哪个范围，全凭实现者自觉。

## 为什么出处必须是制度，不能停留在注释

在 KD-1 落地前，项目里出处纪律只有一条惯例（内核铁律 5"来源写
docstring"）。自由文本注释有三个结构性缺陷，每个都有实账：

- **查不了**：能力卡（kernel_cards，2026-10-19 实测 74 张）要逐卡
  引用出处，机器读不了 prose 就只能留空或手抄——手抄即 #97
  （文档数字必须实测）的温床；
- **守不住**：改公式顺手改坏出处、删模块留下悬空引用，没有任何门
  会红——出处烂掉是静默的；
- **并不动摇实现**：#118 的教训是"确定性内核自身也会错，推导和
  解析期望都可能算错"，裁判必须是独立来源。来源如果只是注释里的
  一句"参考某某"，就没人能机械地核查"真的参考了、核对到位了吗"。

KD-1 的回答是：出处声明留在 docstring（**离公式最近、改公式必经
之地**），但由收集器 AST 扫描结构化成机读注册表，配一致性门把
"忘了同步"变成硬红。

## 两张表的分工：出处 ≠ 精度

| | KD-1 公式出处 | XC-P 精度档案 |
|---|---|---|
| 管什么 | 该公式**引用了谁**（DOI/arXiv/标准号/文献传导链） | 该公式**准到什么**（偏差分档、方向、有效域、越域行为） |
| 条目形态 | source/pointer 声明块 + refs 抽取 | 每内核 6 键 schema（quantities/valid_domain/typical_deviation/refs/behavior/last_verified） |
| 现行规模 | 278 条/225 文件（2026-10-19 实测） | 10 内核（首批） |
| 载体裁决 | 三载体逐字节一致 | 镜像行逐字对照 |

为什么拆成两张表而不是一张：**生命周期不同**。出处一旦写对基本
不变（文献不会改），而精度声明随仲裁/核实活动演化（last_verified、
偏差分档都会重定标）。混在一张表里，每次精度重定标都会搅动出处
面，再生 diff 噪声淹没真实漂移。拆开后各走各的门，但用一条共享
标识符包含钉锁死同源性：XC-P refs 里与内核 docstring 同现的
DOI/arXiv id 必须被 KD-1 收集进 refs（test_formula_provenance 逐条
核对）——两表可以独立演化，不能互相矛盾。

## 为什么是"三载体"而不是一张 YAML

1. **docstring 出处行（人读面，唯一写作点）**。出处必须和公式住在
   同一个文件里：实现者改公式时抬眼就能看到自己承诺过什么来源；
   独立的出处文档必然与代码分叉（方案表系统性落后于代码是 #222
   实证过的系统性模式）。
2. **YAML 注册表（机读单源，生成+人工补录）**。消费面（内核卡
   "出处注册（KD-1）"节、出处巡检、数据湖压缩的指针源、查询 API）
   需要可编程访问；手维护表必然烂（#97 全账都是这类烂法）。所以
   entries 段只由收集器生成，人工只写 `manual_entries` 补录区
   （出处不在 docstring 的场景），再生时逐字保留。
3. **机制模块（core/formula_provenance.py）**。schema 校验/AST 扫描/
   查询面单源；scripts 只是薄壳。core 叶子位置保证分层合法（收集
   逻辑不依赖 service）。

再生方向永远是 docstring → YAML。这个单向性是刻意的：让"改出处"
只有一条路（改 docstring+再生），就不存在"改了表忘了改注释"的
第二种漂移。

## 为什么是幂等再生而不是增量写入

收集器渲染**零时间戳类字段**，同一棵树二跑逐字节 diff=0。这个
性质换来两件事：

- **漂移=字节比较**：`--check` 只需 diff 盘上文件与重扫渲染，"改了
  docstring 忘了再生"从"大概有点旧"变成确定性红（test_formula_provenance
  一致性门 17 测试中的核心三连）；
- **并行安全**：再生内容只由树面决定，两个并行任务先后再生同一
  注册表不会产生合并冲突——这在多任务并行的开发中反复得到验证。

## 诚实口径：宁缺毋滥，null 也是数据

出处制度的底线是 #122 的老原则：**宁可空着，不凑数**。落到这张表上是三条
硬规矩：

- 收集面只收行首标记与"出处见"指针——注释里的内联引文不收，
  覆盖数如实登记，不做"看起来全覆盖"的启发式放宽；
- `access_status` 是 docstring 自声明的词面启发式：判不了就 null
  （2026-10-19 实测 verified 28/unverified 41/null 209——null 占多数
  是制度预期，不是缺陷）；unverified 词面优先于 verified（存疑
  从严）；unverified 占比超阈值（audit_provenance 缺省 0.30，实测
  41/278≈0.147 绿）巡检门红，judged 口径（41/69≈0.59）只报告
  不作门——因为"还没核"和"核了不可达"本来就是常态工作面；
- 注册表自身零物理数字产出（铁律 7 锚：其一致性测试只核对"声明
  与声明一致"，从不裁判物理量真伪）——出处可达性的真伪归文献
  面与 HFSS 仲裁流程，登记制度只负责**可追溯与不漂移**。

## 消费面：登记了谁在用

- 内核卡 builder（`scripts/build_kernel_cards.py`）：每卡按
  kernel_file 过滤渲染"出处注册（KD-1）"节，零命中就显示"0 条"；
- 出处巡检门（`scripts/audit_provenance.py`）：孤儿条目/陈旧条目/
  unverified 占比三 fail 面+两个报告面；
- 数据湖压缩（`service/lake_compact_service.py`）：注册表里引用的
  `runs/…` 路径作为指针源，保护被出处引用的证据目录不被清收；
- 查询面 `formula_provenance()/provenance_summary()`：preflight/
  能力卡/后续 XC-F 的数据入口。

## 给贡献者的推论

- 在 core/ 写任何公式，出处声明是**交付物的一部分**，不是注释
  礼貌——门会替你记住这件事；
- 看到"0 条"的卡节或 null 的 access_status，语义是"如实未登记/
  未判定"，不是"没有出处"——两者都不该被美化；
- 出处声明要写成"可机械抽取"的形态（行首标记+证据面词），写得
  再诚恳但格式不收，等于没写。
